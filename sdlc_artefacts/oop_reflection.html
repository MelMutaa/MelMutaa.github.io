Reflection on Object Oriented Programming

Published on October 20, 2025

Reflection Word Count: 972 words

Introduction

This module has provided a structured and immersive journey into the principles of software design, implementation, and reflection. My capstone project centred on developing a humanoid robot simulation designed to operate within a hospital environment. The goal was to build a Python application that mirrored a real-world support robot’s behaviour — navigating between rooms, delivering items, and reporting its status. The system was designed and implemented using core object-oriented programming (OOP) principles, supported by UML design documentation including class, sequence, and state transition diagrams.

Initially, I began with conceptual design, outlining the system through diagrams and defining key data structures. Early research into human–robot interaction (HRI) and collaborative robotics helped contextualise the simulation. Studying humanoid robots such as Pepper and Moxi deepened my understanding of modularity and state-based decision-making. Translating this conceptual design into executable Python scripts involved creating a modular folder structure (robot.py, scheduler.py, undo_manager.py, tasks.py, sensors.py, and actuators.py), accompanied by unit tests to validate each component’s behaviour. Developing the Scheduler (queue) and UndoManager (stack) provided practical demonstrations of data structure application, while coding the robot’s command-line interface simulated realistic operator interaction.

Throughout the process, I maintained version control using Git and GitHub, learning to manage branches, correct repository issues, and implement .gitignore effectively. These practices reinforced industry-level workflows and improved my confidence in collaborative software development.

WHAT? – Project Outcomes and Critical Incidents

The module culminated in developing a fully functional simulation demonstrating:

  • Polymorphic task management using abstract base classes
  • A design-pattern recommender prototype informed by Palma et al. (2017)
  • Cyclomatic complexity analysis and testing for maintainability
  • Automated testing achieving 95%+ coverage

A critical turning point came during the implementation of the design-pattern recommender system. Initially, I struggled to connect theoretical understanding to practical application. The breakthrough occurred when I used abstract classes for the pattern knowledge base and strategy patterns to control recommendation logic — an approach aligned with Palma et al.’s (2017) research on intelligent pattern selection.

At this stage, UML diagrams became invaluable. Initially, I viewed them as assessment artefacts, but they evolved into working blueprints that shaped my Python code. Translating the state-transition diagram into logic for Robot.run_once() demonstrated how design artefacts can directly guide implementation. Developing automated test modules using assert statements and structured testing files marked another milestone. This approach provided incremental validation and accountability, reflecting professional test-driven development (TDD) standards.

SO WHAT? – Analysis and Interpretation of Learning

Reflecting on this journey, I recognise substantial growth in my technical and reflective capabilities. From a technical standpoint, I progressed from theoretical comprehension to applied mastery of OOP concepts such as encapsulation, inheritance, and composition. Understanding how each module interacted — the coordination between Robot, Scheduler, and UndoManager — and how sensor inputs influenced decisions revealed the importance of design coherence.

Emotionally, the process was non-linear. Errors in Python imports and misplaced Git repositories initially caused frustration and self-doubt. However, persistent debugging transformed these into learning opportunities, supporting Schön’s (1983) notion of the reflective practitioner — learning through reflection in action.

Conceptually, the module redefined my view of design documentation and testing. UML diagrams moved from static visuals to dynamic communication tools. Writing structured test scripts enhanced my accountability and mirrored professional engineering practices.

As Gamma et al. (1994) argue, design patterns establish a shared vocabulary among developers — a concept that empowered clearer team communication. Martin (2000) further emphasises that principles such as cohesion and low coupling underpin sustainable architectures. My project helped reinforce these lessons. Meanwhile, Steidl, Hummel and Juergens (2013) show how meaningful comments improve maintainability; adopting structured docstrings and PEP-8 standards made my own code more transparent and reusable.

Finally, the reflective cycle mirrors Kolb’s (1984) experiential learning stages — active experimentation (coding and debugging) led to concrete experience, reflective observation, and abstract conceptualisation. Each cycle deepened understanding and solidified professional confidence.

NOW WHAT? – Application and Future Learning

This project reshaped how I conceptualise software development — from isolated coding tasks to holistic design, testing, and reflection. Going forward, I will:

  • Apply UML diagrams beyond system design to communicate with stakeholders.
  • Expand my robot simulation with reinforcement learning or path-planning algorithms.
  • Extend my testing framework to include integration and regression tests.
  • Embrace reflective documentation to support continuous learning.

I now develop Python systems that meet professional standards for modularity, readability, and version control. Reflective practice has become integral to this process, acknowledging frustration and experimentation as growth opportunities — aligning with Rolfe et al.’s (2001) reflective model.

From a personal perspective, I developed resilience and self-management through troubleshooting repository issues and restructuring packages. I learned that discomfort often signals learning in progress. The module also heightened my awareness of ethics in system design — particularly in hospital robotics, where reliability and user trust are paramount. This sensitivity will guide my future career in human–technology interaction, where empathy is as crucial as technical skill.

Conclusion

This reflective process has allowed me to consolidate both the technical and personal growth achieved throughout the module. The humanoid hospital robot project acted as an authentic learning environment where theoretical principles were applied to practical challenges.

Through this module, I have not only enhanced my technical proficiency in Python, UML, and software architecture but also cultivated a reflective and professional mindset. The iterative nature of development and debugging strengthened my resilience and critical thinking, aligning with Schön’s (1983) notion of reflection-in-action. Applying Kolb’s (1984) experiential learning cycle enabled me to transform mistakes into insights, while Rolfe et al.’s (2001) framework helped structure these reflections into actionable learning outcomes.

Overall, this module has shaped my identity as both a reflective learner and a developing software engineer. I now approach programming as a continuous cycle of design, experimentation, reflection, and improvement. Moving forward, I intend to apply these reflective practices in collaborative and industry contexts, ensuring that each project contributes not only to technical output but also to my ongoing personal and professional evolution.
